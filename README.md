# Калькулятор размещения облигаций

Тестовое задание на стажировку 3P B2B. Рабочий проект Дарьи Шевченко.

Калькулятор должен выбирать распределение объёма сделки между институциональными инвесторами, частными инвесторами на размещении, покупкой для перепродажи и удержанием до погашения.

**Статус:** реализованы четыре канала, расчёт распределения, ROE/IRR, проверка порогов, MILP-поиск и отдельный глубокий поиск Differential Evolution с несколькими запусками. Интерфейс пока не реализован.

Текущие ограничения, методика и открытые вопросы: [MODEL_ASSUMPTIONS.md](MODEL_ASSUMPTIONS.md).

Независимая проверка: [отчёт и сверка с ТЗ](research/INDEPENDENT_AUDIT.md), [план проверки](VERIFICATION_PLAN.md), [история вопросов](OPEN_QUESTIONS.md). Решения A1–A9 приняты и записаны в разделе 14 ограничений модели. Четыре базовых максимума подтверждены в рамках модели и сетки; это не означает готовность интерфейса и всего задания к сдаче.

Данные задания вымышленные. Условия задания и принятые нами допущения разделены в документе модели.

## Четыре функции

```python
from dataclasses import asdict, replace
from bond_calculator import load_deals, load_system, balance_for_resale

deal = load_deals()["A"]
system = load_system()
x = 1_000_000_000  # Объём этого канала, рубли

result = balance_for_resale(x=x, deal=deal, system=system)
print(result.profit_before_tax)
print(result.standalone_net_profit)
rows = [asdict(month) for month in result.months]  # Готово для таблицы интерфейса

# Исходные данные не изменяются; создаём новый сценарий.
slower_deal = replace(deal, monthly_resale_volume=100_000_000)
new_result = balance_for_resale(x=x, deal=slower_deal, system=system)
```

Все функции имеют аргументы `(x, deal, system)`:

| Функция | Канал |
| --- | --- |
| `institutional_placement` | Продажа институционалам на размещении |
| `retail_placement` | Продажа рознице на размещении |
| `balance_for_resale` | Покупка для перепродажи |
| `hold_to_maturity` | Удержание до погашения |

Результат содержит прибыль и месячные строки: остатки позиции, продажи, погашение, капитал, компоненты дохода и расхода, налог. **Номинал не входит в прибыль.**

Налог канала — оценка при его отдельном использовании. Для общей сделки используйте `calculate_allocation(x1, x2, x3, x4, deal, system)`: налог считается после суммирования прибыли каналов за каждый месяц. Складывать `standalone_net_profit` четырёх каналов в общем случае неверно.

Отдельные функции проверяют спрос/лимит своего канала. Общая функция дополнительно проверяет суммарный лимит, выпуск и шаг распределения 1 млн ₽. Во время исследования отдельный канал можно считать с произвольным объёмом.

## Что меняется

| Группа | Где хранится | Кто меняет |
| --- | --- | --- |
| Объёмы `x1…x4` | Отдельные аргументы расчёта | Сейчас пользователь; позднее оптимизатор |
| Условия сделки: выпуск, срок, купон, комиссия, PD, риск-вес, лимит, спрос, темп продаж, месяц размещения | `data/deals.json`, объект `Deal` | Пользователь при редактировании условий или сценария |
| Общие настройки: КС по месяцам, налог, фондирование, LGD, норматив капитала, комиссии, риск-вес перепродажи, пороги, шаг | `data/system.json`, объект `SystemParameters` | Пользователь через общие/расширенные настройки |
| Рейтинг и название | `data/deals.json` | Информационные поля; сами не определяют PD и риск-вес |

Данные ТЗ — стартовые значения, а не неизменяемые константы. Ставки хранятся долями единицы: `0.14` = 14%, `0.002` = 0,2 процентного пункта; деньги — в рублях. Купон задаётся как `floating` со спредом либо `fixed` с фиксированной ставкой. Неиспользуемое поле равно `null`.

Четыре функции прибыли сами не проверяют доходность. Для оценки распределения используйте `calculate_returns`; для подбора объёмов — `optimize_milp`. Обязательные правила календаря и погашения описаны в модели; они не являются случайными параметрами оптимизатора.

## Доходность и MILP

```python
from bond_calculator import load_deals, load_system, calculate_allocation, calculate_returns
from bond_calculator.optimization import optimize_milp

deal, system = load_deals()["A"], load_system()
allocation = calculate_allocation(1e9, 1e9, 1e9, 1e9, deal, system)
metrics = calculate_returns(allocation, system)
print(metrics.roe, metrics.irr.annual, metrics.accepted, metrics.status)

result = optimize_milp(deal, system, time_limit=15)
print(result.volumes, result.status, result.optimality_proven)
if result.metrics:
    print(result.metrics.net_profit, result.metrics.roe, result.metrics.irr.annual)
```

- ROE = вся чистая прибыль / сумма занятого капитала в рубль-годах. Месячные ROE — диагностика, не ограничения.
- Потоки собственного капитала: первоначальное выделение с минусом, затем чистая прибыль и высвобождение капитала. Номинал дополнительно не прибавляется.
- IRR считается в месяцах, годовая = `(1 + monthly_irr)**12 - 1`.
- Поддерживается уникальная IRR для потоков с одной сменой знака с минуса на плюс, включая несколько начальных отрицательных потоков. При нескольких сменах знака возвращается `nonconventional`, а не произвольно выбранный корень. Это не утверждение, что корней обязательно несколько: такой случай требует отдельного анализа.
- Без капитала положительная прибыль допускается; ROE/IRR и их отдельные проверки равны `None`, статус `accepted_no_capital`.
- `roe_passed`, `irr_passed`, `accepted`, `status` объясняют прохождение порогов. Для ставок используется численный допуск `1e-9` в долях единицы.
- В первом месяце с разовыми доходами появляется информационное пояснение; доступны месячные ROE и доля прибыли первого месяца. Это не фильтр оптимизации.

MILP содержит ограничения ROE и NPV по пороговой IRR. На поддерживаемых денежных потоках NPV-проверка эквивалентна порогу IRR. Кандидаты обязательно пересчитываются обычными функциями и проходят фактическую проверку IRR/ROE.

Статусы оптимизатора:

| Статус | Значение |
| --- | --- |
| `optimal` | Допустимое решение и подтверждённый максимум с численным допуском не более max(1 ₽, 1e-9 × прибыль) |
| `incomplete` | Расчёт остановился по времени или кандидат релаксации не прошёл проверку; возвращён лучший проверенный допустимый вариант, если найден |
| `no_acceptable_allocation` | Доказано отсутствие положительного допустимого варианта |

Возвращаются верхняя граница прибыли и абсолютный разрыв, когда их можно определить. Если нетипичный поток не позволяет подтвердить IRR, оптимизатор не объявляет его допустимым и не обещает глобальный максимум. Нулевой вариант не выдаётся за успешную сделку. Общий лимит времени относится ко всему поиску; подготовка и финальная проверка могут немного увеличить фактическое время.

## Глубокий поиск

Отдельный модуль `bond_calculator/deep_optimization.py`; существующий MILP не изменён.

```python
from bond_calculator.deep_optimization import optimize_deep

result = optimize_deep(deal, system, runs=4, seed=42,
                       maxiter=800, popsize=24, run_time_limit=20)
print(result.volumes, result.metrics, result.runs)
```

Четыре последовательных запуска используют seed 42–45. Каждый новый запуск получает лучшего проверенного кандидата из предыдущих, но не получает результат MILP. После запуска выполняется локальная целочисленная доводка. Во всех оценках действуют ограничения объёма, спроса, лимита и доходности; ускоренный расчёт проверен на соответствие исходным функциям. Окончательное решение независимо пересчитывается через `calculate_allocation` и `calculate_returns`.

Возвращается `feasible` либо `no_feasible_found`. Последний статус означает, что поиск не нашёл допустимого варианта, а не доказал его отсутствие. `optimality_proven` всегда `False`, даже при сходимости всех запусков. Базовый комиссионный кандидат проверяется отдельно. У каждого запуска сохраняются seed, время, число оценок, число поколений, признак сходимости и проверенная прибыль.

`run_time_limit` относится к эволюционной части одного запуска и проверяется между поколениями; подготовка, проверка конечной популяции и доводка могут увеличить фактическое время. Повторяемость seed ожидается при одинаковых версиях библиотек и без срабатывания временного ограничения.

